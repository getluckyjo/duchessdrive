# Drive audit, cleanup, and what "organised" would cost

Three things came out of the 2026-08-29 session: the drinkdope.com accounts are
more complete than they looked, one measurement trap wasted an hour and will
waste another if it is not written down, and the cleanup now running changes
what this backup *is* in a way the verify script did not account for.

## 2. The measurement trap: two remotes

There are two rclone remotes, and only one of them can impersonate:

    duchess:      plain OAuth  - --drive-impersonate is SILENTLY IGNORED
    duchess-sa:   service account - delegation works

`common.sh` defaults to `REMOTE=duchess`. So this:

    rclone size duchess: --drive-impersonate sebastian@drinkdope.com

does not measure Sebastian's Drive. It measures whoever holds the OAuth token,
and reports a confident, wrong answer. Two different accounts came back with an
identical 895.604 GiB before the cause was obvious — that identity is the tell.

**Always pass `REMOTE=duchess-sa` for anything per-account**, or check first:

    rclone config show duchess-sa | grep -q '^service_account_file' && echo delegated

`03-copy-drive.sh` already refuses this combination, but only when
`accounts.tsv` holds more than one active account — a single-account run slips
straight past the guard. The 2026-08-19 "UNLICENSED" diagnosis for the dope
accounts may well have been made this way; it happened to be correct for
`sebastian@` anyway.

## 3. Verify no longer means what it used to

`04-verify.sh` runs `rclone check --one-way` from the live account to the disk.
It reports files present upstream but absent locally.

That was the right check while the disk was a faithful per-account mirror. It
is the wrong check the moment `09-dedupe.sh` or `10-clear-dumps.sh` runs,
because a file that legitimately exists once on the disk still exists under
every account that shared it upstream. **Every reclaimed copy now reads as a
missing file.** Tens of thousands of them.

The danger is not the noise. It is the obvious response to the noise:
`03-copy-drive.sh` will cheerfully re-download every deleted duplicate and undo
the entire cleanup, slowly, overnight, while looking like it is repairing
something.

`04-verify.sh` now detects that deletions have happened and says so before it
prints a single difference. Read that warning before acting on the output.

## 4. What "organise the drive properly" would cost

The disorder has three layers. Two are being fixed; the third is a decision,
not a task.

**Layer 1 — redundant copies inside ex-staff dumps.** Six dumps, 424.9 GiB:

    248.8 GiB  inus@       <- marike@theduchess.co.za
    157.3 GiB  johannes@   <- inus@theduchess.co.za 2026-08-07T15:23:32.980Z
     10.8 GiB  tania@      <- Deleted Google Account Transfers
      6.8 GiB  inus@       <- talita@theduchess.co.za
      1.1 GiB  inus@       <- reder@theduchess.co.za
      0.2 GiB  inus@       <- caitlin@theduchess.co.za

Being cleared now by `10-clear-dumps.sh`, which only removes a file when an
identical copy survives outside every dump.

**Layer 2 — the same corpus held three times.** `The Duchess Brand` under
`tania@` (242.8 GiB), `The Duchess` under `johannes@` (190.1 GiB) and the
overlap in `inus@` are largely the same company files seen from three staff
accounts. `09-dedupe.sh --execute` collapses these.

**Layer 3 — the account-shaped layout itself.** This is the real question, and
the answer is uncomfortable: *layers 1 and 2 have already destroyed the meaning
of the layout.* Once dedupe picks a winner, `drive/<email>/` is no longer that
person's Drive. It is an arbitrary shard of one corpus, determined by whichever
account happened to rank first in `KEEP_ORDER`.

So "organise properly" is not cosmetic tidying. It is the decision to stop
treating this disk as a mirror and start treating it as an archive:

| | Mirror (today) | Archive (organised) |
|---|---|---|
| Layout | `drive/<email>/<path>` | by project, one copy each |
| `04-verify.sh` | works | meaningless — rewrite or retire |
| `03-copy-drive.sh` re-run | incremental | re-downloads everything |
| Finding a file | look under three accounts | look in one place |

**Recommendation:** finish layers 1 and 2, then decide layer 3 deliberately —
do not drift into it. If the disk is a disaster-recovery copy of a Workspace
org, keep the account layout and accept the duplication you have not yet
removed. If it is the surviving record of a company whose subscription is
already cancelled — which is what it actually is — then the archive layout is
correct, and `04-verify.sh` should be replaced by a self-contained integrity
check (hash manifest on the disk) rather than a comparison against a Google
account that will not exist much longer.

That second reading is almost certainly right. But it retires a working safety
net, so it is not a change to make unattended, and it is not made here.
